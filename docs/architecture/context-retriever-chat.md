# Context Retriever in the camera adviser

The adviser discovers the service’s autogenerated MCP tools and lets the model
choose each call. This is the corrected design approved on 2026-09-30; it
replaces the earlier handwritten `get_purchase_history` wrapper.

## Design

1. Validate the selected demo shopper against the saved session owner.
2. Supply RAM session context, recalled preferences, Playbook guidance and the
   selected `shopper_id` to the model. Do not supply an empty purchase-history
   placeholder: orders have not been retrieved yet.
3. Call MCP `tools/list` with that shopper’s scoped agent key. Follow discovery
   cursors and preserve generated names, descriptions and JSON input schemas.
   Add the local `search_catalogue` tool, which searches the full catalogue.
4. Let the model select a tool and arguments. Validate arguments against the
   discovered schema, then invoke that exact name through MCP `tools/call` with
   the same shopper’s key. No hidden product fetches or prescribed call sequence.
5. Return the tool’s JSON result, including pagination metadata, to the model.
   Validate any returned shopper/order records before model use. Collect product
   cards only from returned product records or local catalogue results.
6. Repeat for at most six calls, then request an answer with further tools
   disabled. Save the exact model request and exchanges for **What the model
   saw → Available tools / Tool calls**.

The current surface exposes 16 generated tools: entity ID lookups, filters,
counts, text search, set operations and relationship expansion. The application
adds one local catalogue tool. These names are discovered, not hard-coded in the
runtime adapter. Generated tools retain `strict: false` when exposed as Responses
functions so their original optional fields and schemas are not rewritten.

The synchronous adapter uses the existing pooled `httpx.Client` and the
Context Retriever service’s stateless JSON-RPC interface, matching the installed
official SDK transport. JSON Schema validation supports nested and conditional
schemas; schema resolution must not initiate arbitrary network reads. The
optional SDK remains the independent service-check client.

## Boundaries and failures

The server selects credentials independently of model arguments. Generated ID
and filter parameters can name records, but cannot change the key’s access tags.
Discovery is scoped per turn and never shared between shopper credentials.
Foreign shopper records, invalid order dates, non-fictional fixture orders,
malformed schemas/results, transport failures and unrecognized MCP errors fail
explicitly. Known unindexed-field errors return sanitized feedback so the model
can revise its query. Missing/denied ID lookups return the same neutral error
without revealing whether a foreign record exists.
Errors sent to the browser contain no service response bodies or credentials.
Fatal retrieval failures occur before conversation event writes; the UI reports
that retry is safe. A handled query error remains in the captured tool exchange
and may lead to a corrected query or an explicit unavailable-record answer.
There is no fixture fallback.

`CTX_MCP_URL`, `CTX_ALEX_AGENT_KEY` and `CTX_JORDAN_AGENT_KEY` are runtime settings.
Chat never uses the admin key or direct service database URL. Shutdown closes the
connection pool. Demo shopper selection is a teaching control, not authentication.

Empty successful results remain empty. `has_more`, offsets and counts reach the
model so it can choose subsequent pages. The model is instructed to acknowledge
partial results when the call budget prevents completion. The seeded Product
entity contains three order-linked products (including an explicit demo microphone); recommendations use the separate
local catalogue. Orders establish historical purchases, not current ownership,
compatibility, price or stock.

Legacy saved conversations still deserialize with their old purchase fields and
captured tool names. Their evidence is historical; new replies use discovery.

## Shipment demo extension (September 30)

The approved delivery demo adds Alex's September microphone purchase, the
`Purchase.shipment` relationship and a shopper-scoped Shipment entity. All eleven
fixtures are read from the configured service. The runtime validates shipment
identity, shopper, status, dates, timezone-aware event time and the explicit
fictional marker. Purchase references and Shipment records are validated as
different shapes even though both contain `order_id`. Demo product records are
validated and passed to the model but do not create links to nonexistent local
catalogue pages.

The model must identify an item through purchase/product evidence and retrieve
shipment status afresh for delivery questions. Prior assistant messages and RAM
memories do not establish current delivery status. Replies should name the item,
event and explicit revised date, with no unsupported investigation/refund offers.
This is prompting plus verified sample behaviour, not a guarantee for every LLM
response.

The setup script supports guarded atomic migration, model publication and two
repeatable shipment snapshots. `context-check` verifies 27 reads and access
boundaries against the initial delayed state. The service exposes 16 generated
tools plus the local catalogue tool. See the [presenter walkthrough](../demos/context-retriever.md).

## Earlier purchase-only verification

The automated chat tests use the actual model loop, MCP adapter and FastAPI route
with controlled HTTP transports. They cover both shoppers in all memory modes,
original schema forwarding, model-selected relationships, one remote invocation
per selected tool, pagination metadata, product cards and captured exchanges.
Failure cases include invalid arguments, foreign/malformed records, expired keys,
timeouts, duplicate tools, incorrect JSON-RPC IDs and unresolved schema references.
A regression also prevents empty legacy purchase placeholders in new model inputs.

Live verification uses the configured Context Retriever surface on `sam-test-db`,
OpenAI, Playbook, RAM and local Redis, with a separate QA owner prefix. Alex’s
purchase question selected `count_purchase`, `filter_purchase` and
`get_product_by_id` and returned the Sony ZV-E10 dated 2026-04-18. The model chose
this sequence; it was not supplied by a purchase wrapper. Jordan selected
`filter_purchase` and `get_product_by_id` and received the JJC strap dated
2026-06-03. A relationship request selected `expand_results` with entity Purchase
and relationship `product`; its result contained only Jordan’s linked product ID.
Alex’s accessory follow-up used local catalogue search. Alex’s session restored
successfully, and the UI showed 14 available tools with the actual exchanges.

The final local checks passed: 268 Python tests (30 opt-in skips), 25 frontend
tests, Ruff, strict mypy across 42 source files, TypeScript and the Vite build.
All 14 independent live service probes also passed, including foreign-shopper
access checks. Independent review found a dangling schema-reference failure; it is now covered
and returns a safe error without fetching remote schema resources.

Early live attempts returned generic retrieval failures before diagnostic tracing;
their exact upstream cause was not captured. Another attempt incorrectly inferred
no orders from an empty legacy placeholder; that model input was removed and
regression-tested. The later traced browser checks above passed.

The [earlier UI review](context-retriever-ui-checks.md) remains a historical record
of the preceding implementation and its grounding limitations. Correct retrieval
and captured MCP evidence do not prove that every generated technical claim is
supported, or that RAM background extraction has reconciled old information.

A subsequent [UI and teaching review](context-retriever-pedagogy-checks.md) records
varied queries, corrected query-error handling, clearer source labels, and the
remaining answer-quality limitations.
